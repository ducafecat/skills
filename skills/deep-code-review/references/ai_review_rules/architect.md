# 架构检查

## 检查范围

- 模块职责是否被打破，业务规则是否放入错误层级。
- 依赖方向是否反转、形成循环，或让上层依赖下层实现细节。
- 数据流、所有权和状态来源是否出现多套事实来源或隐式耦合。
- 公共接口、共享 abstraction 与扩展点是否保持清晰稳定的契约。
- 新 abstraction、parameter、wrapper 或中间层是否没有当前需求支撑。

## 成立条件

- 说明本次变更引入的具体依赖或职责问题，以及它如何影响现有调用方、测试或后续修改。
- 只有在当前 diff 已经造成结构性成本时才报告；“未来可能扩展”不足以成立。

## 不报告

- 个人偏好的目录、命名、设计模式或重构方式。
- 可由小范围正确性修复解决、没有模块边界影响的问题。
- 以架构名义报告安全、性能或产品契约问题。
